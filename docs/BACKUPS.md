# Резервное копирование и восстановление

## Что сохраняется

- Deploy перед отправкой на VPS сохраняет проверенную сборку `out`, SHA-256 каждого файла и коммит. Если сохранение артефакта не удалось, публикация не начинается.
- Backup еженедельно по воскресеньям в 00:17 UTC (03:17 Минск) сохраняет сайт, базу и файлы. Сборка сайта создаётся из текущей main, а не из снимка диска VPS. Ручные изменения на VPS, nginx, SSL и системные настройки в неё не входят. Дополнительная копия сборки сохраняется перед каждой публикацией через Deploy.
- Отдельная задача Backup сохраняет роли PostgreSQL, схему, данные (включая Auth), дополнительную схему auth/storage, исходные миграции и содержимое всех обычных Storage buckets. Закрытые файлы скачиваются через серверный ключ. Архив шифруется до отправки в GitHub. Секретный ключ расшифровки не хранится в GitHub.
- Срок хранения GitHub Actions artifacts — 90 дней. Это внешняя копия относительно VPS и Supabase, но удаление репозитория уничтожит и её. Для независимой долгосрочной копии скачивайте зашифрованные архивы на отдельный носитель.
- Сайт и база копируются раздельно. База и Storage не имеют общей транзакции: для полного согласованного восстановления нужен интервал без редактирования материалов и загрузки файлов. Отсутствующий/изменившийся во время скачивания файл останавливает копирование. Не считать запуск успешным, пока обе задачи не зелёные.

## Однократное включение базы и файлов

В Settings → Secrets and variables → Actions нужны:

- `SUPABASE_DB_PASSWORD`: сохранённый пароль PostgreSQL без дополнительного кодирования. Workflow сам формирует URI Session pooler с percent-encoding и TLS. Для нестандартного подключения можно вместо него задать `SUPABASE_DB_URL` с полным URI.
- `SUPABASE_SERVICE_ROLE_KEY`: существующий серверный service_role key проекта. Не публичный publishable/anon key.

Не вставлять эти значения в исходники, issues, логи или чат. Репозиторий на момент проверки публичный; в артефакты базы допускается только шифротекст. Участник с правом изменения workflows потенциально может использовать Actions secrets: доступ к исходникам требует доверия.

Запустить Backup вручную и проверить обе задачи. До первого успешного скачивания и восстановления базы/файлов автоматическое резервирование этих данных не считать настроенным. Проверять Actions после сбоев; владелец должен включить уведомления о неуспешных workflows в личных настройках GitHub.

## Откат сайта

1. Actions → Deploy (или Backup) → выбрать успешный запуск и `site-RUN_ID-ATTEMPT`.
2. Actions → Rollback site → Run workflow → указать числовой run_id и точное имя артефакта.
3. Workflow проверяет SHA-256 архива, безопасно распаковывает только out и manifest, проверяет полный список файлов и публикует через существующий DEPLOY_KEY.
4. Проверить askacademy.ru. База и файлы Supabase не изменяются. Следующий push в main снова опубликует main; для постоянного отката отдельно сделать git revert нужного изменения.

Срок артефакта истёк — собрать нужный Git-коммит после проверки совместимости с текущей базой. Не откатывать схему вместе с frontend автоматически.

## Расшифровка и проверка данных

Скачать оба файла из `encrypted-data-RUN_ID-ATTEMPT` на доверенный компьютер.

```sh
sha256sum -c database-and-files.askbackup.sha256
node scripts/backup/crypto.cjs open database-and-files.askbackup restored.tar.gz /secure/path/restore-private.pem
```

AES-256-GCM проверяет целостность и подлинность; при ошибке расшифровки готовый файл не создаётся. Без закрытого RSA-ключа восстановление невозможно. Сохранить ключ отдельно на защищённом внешнем носителе. Не отправлять его в GitHub или в общие папки.

## Восстановление базы и файлов

Сначала восстановить в отдельный Supabase-проект, а не поверх рабочего. Следовать актуальной инструкции Supabase https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore . Роли, schema.sql и data.sql восстанавливаются с ON_ERROR_STOP и одной транзакцией; для данных отключаются пользовательские триггеры через session_replication_role. Пользовательские триггеры Auth и политики Storage восстанавливаются из миграций; `managed-schema.sql` — дополнительный исходник для сравнения, не выполнять целиком поверх системных схем. Пароли пользовательских LOGIN-ролей и настройки провайдеров входа требуют отдельной настройки.

Storage: manifest.json содержит buckets (включая public/private), исходные имена объектов, metadata, размер и SHA-256. Байты находятся в objects под безопасными хеш-именами. Перед загрузкой сверить все хеши. Создать buckets с исходными настройками и загрузить каждый объект под исходным именем через Storage API. Не восстанавливать одни записи storage.objects без самих файлов.

Проверить количество записей ключевых таблиц, вход, права отделов, учебные материалы, попытки тестов и скачивание приватного файла. Только после успешной проверки согласовывать замену рабочей базы. Полный тест восстановления в новый Supabase-проект требует отдельного проекта и не выполняется автоматически на production.

Не входят: Supabase dashboard settings, OAuth client secrets, Edge Function secrets, Vault encryption root key, инфраструктура VPS/DNS/TLS. Их восстановление требует настроек владельца. Для текущего проекта хранить отдельный перечень настроек без публикации секретов.
